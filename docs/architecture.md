# Architecture

## Layers (STM32 cluster)

Each layer only calls the layer below it, and the hardware registers are only touched in `mcal/`. The names follow AUTOSAR Classic loosely.

| Layer | Directory | Content |
| --- | --- | --- |
| Application | `app/` | `cluster` (signal conversion, warnings, fuel filter, odometer), `dashboard`, `main` (super loop) |
| Services | `services/` | `com` (RX dispatch, E2E check, timeout monitoring, ClusterStatus TX), `log` |
| Shared | `common/` | `can_matrix` (pack/unpack), `e2e` (CRC8 + alive counter), compiled for STM32, ESP32 and the PC |
| ECU abstraction | `ecual/`, `gfx/` | `ili9341`, drawing primitives, font |
| MCAL | `mcal/` | `rcc`, `gpio`, `systick`, `uart`, `adc`, `spi`, `bxcan`, `iwdg` |

## Execution model

Interrupt handlers only move data or count events. Everything else runs in one main loop, so the application never shares data with another thread of execution except through the two ISR queues.

| What | When | Work |
| --- | --- | --- |
| CAN RX0 ISR | each received frame | copy FIFO0 into a 32-frame queue |
| CAN SCE ISR | error-passive / bus-off | count bus-off events |
| USART1 ISR | TX empty / RX not empty | move bytes between the ring buffers and the data register |
| SysTick ISR | 1 ms | increment the tick counter |
| Main loop, every pass | | drain the CAN RX queue (max 8 frames per pass) |
| Main loop, 10 ms | | message timeout monitoring |
| Main loop, 20 ms | | cluster logic, dashboard redraw |
| Main loop, 100 ms | | ClusterStatus TX, heartbeat LED |
| Main loop, 1 s | | status line on the debug UART |

Each time slot plans its next release from the previous one (`next += period`), so the period does not drift when a pass runs late. Slots start with different offsets so they are not all due in the same pass.

## Interrupt priorities

| IRQ | Priority | Why |
| --- | --- | --- |
| CAN RX0 | 5 | the hardware FIFO holds only 3 frames |
| CAN SCE | 6 | |
| USART1 | 7 | 115200 baud leaves 87 µs per byte |
| SysTick | 10 | only increments a counter |

## Data flow of one speed value

1. The ESP32 packs `VehicleSpeed` into 0x100, adds the alive counter and CRC8, and sends it every 20 ms.
2. bxCAN filter bank 0 (identifier list) accepts the frame. The RX0 ISR copies it into the queue.
3. `com_poll_rx` takes it from the queue and runs `e2e_check`. Only a frame with a correct CRC and a plausible counter updates the signal and restarts the 100 ms timeout.
4. `cluster_update_20ms` converts the raw value to km/h and updates the odometer and warnings.
5. `dashboard_update` redraws the speed digits only if the text or colour changed.
6. `cluster_send_status_100ms` reports the same snapshot in ClusterStatus 0x300.

## Design decisions

- **No framebuffer.** 320 x 240 x 2 B = 150 KB does not fit in 20 KB of RAM. Widgets remember what they last drew and repaint only on change, and text is drawn one scan line at a time.
- **16-bit SPI frames for pixels.** The ILI9341 expects RGB565 MSB first, which a 16-bit SPI frame sends as-is.
- **The timeout restarts only on E2E-valid frames.** A sender that keeps transmitting corrupted data is treated like a lost sender.
- **Shared code between nodes.** `can_matrix` and `e2e` compile unchanged for Cortex-M3, Xtensa and the PC, so sender, receiver and tests cannot drift apart. The DBC file is checked against the C code with vectors generated by cantools.
- **Testable COM layer.** `services/com.c` runs unchanged in the host tests against `test/fake_bxcan.c`, which replaces the hardware driver.
